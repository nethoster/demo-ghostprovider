# Стенд верификации systemd 261 (Arch) — эмпирические результаты

Дата: 2026-08-23. Машина: user-session systemd 261.2-1-arch.

## 1. Эскейп EnvironmentFile (двойные кавычки)

| Записано в файл | Значение у процесса | Вывод |
|---|---|---|
| `plain$dollar`   | `plain$dollar`  | `$` вербатим, раскрытия переменных НЕТ |
| `escaped\$dollar`| `escaped$dollar`| `\$` схлопывается в `$` |
| `double$$dollar` | `double$$dollar`| `$$` НЕ схлопывается |
| `percent%%p`     | `percent%%p`    | `%%` НЕ сворачивается (%-спецификаторы не работают в env-файле) |
| `bs\\bs`         | `bs\bs`         | `\\` → `\` |
| `dq\"dq`         | `dq"dq`         | `\"` → `"` |
| `newline\ntest`  | `newline\ntest` | `\n` НЕ разворачивается (литеральный бэкслеш-n) |
| `unknown\zescape`| `unknown\zescape`| неизвестный эскейп сохраняется вербатим |
| `trail\` перед `"` | СЛОМАНО       | закрывающая кавычка съедена, состояние кавычек переносится на следующие строки и загрязняет их разбор |

### Правильный эскейпер для EnvironmentFile (двойные кавычки)
- `\` → `\\`
- `"` → `\"`
- всё остальное ВЕРБАТИМ (`$`, `%`, `${...}` не трогать)
- значения с переводами строк отклонять (не кодировать)

### Вердикт по коду Python
- `secrets.py:_escape`: `%`→`%%` = РЕАЛЬНЫЙ БАГ (портит значения с `%`);
  `$`→`\$` избыточен, но не вреден (даёт тот же литеральный `$`)
- `systemd.py:_escape_unit_value`: `$$`/`%%` корректны ТОЛЬКО для контекста
  unit-файла (Environment=/ExecStart=) — там %-спецификаторы и ${VAR}
  раскрываются; в env-файлах — нет. Два контекста = два эскейпера.

## 2. Семантика состояний старта

- Медленный сервис (oneshot sleep 8): `is-active` = `activating` на
  t+0.5…4c, rc=**3**; после завершения — `active`, rc=0.
- Падающий сервис (/bin/false): `failed` через ~1.5с, rc=**3**,
  `show -p SubState`=failed, `-p Result`=exit-code.
- ВАЖНО: rc у `activating` и `failed` ОДИНАКОВЫЙ (=3). Различие только
  по строке. Exit-code использовать нельзя.
- Однократная проверка после sleep 5 = ложный «crashed» для сервисов,
  стартующих дольше 5с — подтверждено.

### Правильный поллинг старта
- опрос `is-active` каждые ~500мс, бюджет ~30с
- `active` → успех немедленно
- `activating` → ждать дальше
- `failed`/`inactive` → провал сразу: собрать journalctl + `show -p
  Result -p ExecMainStatus`
- таймаут при `activating` → отдельный диагноз («не стал active за N с»),
  не «crashed»

## 4. Чистая зачистка прерванных деплоев (приложение)

Деплой идёт в отдельном потоке TUI; при выходе из панели/гибели процесса/
выключении машины его in-process откат (`rollback_failed`) не выполняется.
Дизайн гарантии «чистого удаления»:

- On-disk журнал `~/.local/state/demo-ghostprovider/deploy-journal.json`:
  запись `deploying` → `registering`/`registered` → удаление при завершении
  `run_deployment` (успех или штатный откат). Оставшаяся запись = деплой
  прерван вне процесса.
- `cleanup_stale` идемпотентна и переиспользует штатные `remove_unit`,
  `remove_env_file`, `wipe_project_dir` (guard parent == services_dir) —
  поэтому безопасна при гонке с доживающим воркером.
- Реконсиляция (`reconcile_stale`) на следующем запуске: `registered` — только
  забыть; `registering` с уже записанным `state.json` — сервис живой, не
  трогать; `registering` без записи и `deploying` — полная зачистка. Живые
  зарегистрированные сервисы при ребуте НЕ удаляются (unit-пары contain
  `Restart=always` + `WantedBy=default.target`).
- Если немедленная зачистка не смогла удалить проектное дерево (его держит
  ещё живой sandbox-build), запись журнала сохраняется → повтор следующего
  запуска.
- SIGTERM/SIGHUP обрабатываются через signal-hook в потоке, рутятся в цикл
  событий как `Msg::Terminate` (та же зачистка + корректное восстановление
  терминала). Ctrl+C в raw-mode TUI — это key event, обрабатывается там же.
